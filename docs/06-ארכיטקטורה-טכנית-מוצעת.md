# 06. ארכיטקטורה טכנית מוצעת

> זהו פרק "מוצע" בלבד — ההחלטות הסופיות אמורות להתקבל בשלב האדריכלות מול סוכן הפיתוח (למשל שלב ה-Architecture ב-BMad, ראו תוכנית העבודה).

## רכיבים מוצעים

- **Frontend:** אפליקציית web פשוטה (React) — מסך העלאת קבצים, מסך תצוגה מקדימה/עריכה של הבנק המרוכז, מסך ייצוא.
- **Backend:** שירות API (Python/FastAPI מומלץ בשל ספריות עיבוד PDF/docx בוגרות, לחלופין Node.js) שמנהל את זרימת העיבוד: חילוץ טקסט מ-PDF → קריאה למודל שפה לסיווג ואיחוד → בניית הבנק המרוכז → יצירת קובץ פלט.
- **מנוע הסיווג/איחוד:** קריאה ל-API של מודל שפה (LLM) עם פלט מובנה (JSON) לכל שאלה: סוג, נושא, זיהוי כפילות/משפחה, מקור.
- **יצירת מסמכים:** מודול ייעודי ליצירת docx/PDF (ראו פרק 05).
- **Deployment:** Railway, בהתאם להמלצת מנחה הסדנה.

## עקרונות מנחים

- אין להמציא את הגלגל: שימוש בספריות/כלים בשלים וקיימים (PDF parsing, docx generation) ולא כתיבה מאפס.
- הימנעות מתלות בחבילות לא בשלות (פחות מ-300 כוכבים ב-GitHub) — לפי הנחיית המנחה.
- שימוש בדאטה קיים (קובץ ה-Markdown המרוכז שכבר נוצר ידנית עבור מערכות הפעלה) כבסיס לבדיקות/דמו, לחיסכון זמן.

## החלטות פתוחות

**נדרשת החלטה:** בחירת ה-LLM/API לעיבוד (לדוגמה Anthropic API עם Claude) — כולל בחירת דגם ספציפי, ומי מהצוות מספק את מפתח ה-API/מנצל תקופת ניסיון (trial) שטרם נוצלה, לפי הנחיית המנחה.

**נדרשת החלטה:** שפת/פריימוורק ה-Backend הסופיים (Python/FastAPI מול Node/Express) — תלוי בנוחות הצוות ובכלי ה-vibecoding שבשימוש (BMad/Superpowers פועלים היטב עם שניהם).

**נדרשת החלטה:** האם נדרשת בסיס נתונים (למשל SQLite) לשמירת פרויקטים בין הפעלות, או שה-MVP יעבוד session-based בלבד ללא שמירה בין ביקורים (העלאה → עיבוד → הורדה, בלי היסטוריה)? המלצה: session-based בלבד ל-MVP, בהתאם לדחיפות הזמן.

**נדרשת החלטה:** ניהול העלאת קבצים גדולים/מרובים (מבחני PDF יכולים לשקול 300–450KB כל אחד לפי הניסיון הקודם) — הגבלת מספר קבצים/גודל כולל לבקשה בודדת, כדי להימנע מחריגה ממגבלות ה-context של המודל.
